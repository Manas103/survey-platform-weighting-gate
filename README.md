# In-Product Survey Platform with Weighting and a Pre-Launch Instrument Gate

A Python simulation of the four pieces of a real in-product intercept survey
program that sit upstream of any analysis: stratified intercept sampling
with exposure caps over a simulated 200,000-user panel, a nonresponse-biased
response simulation, raking (iterative proportional fitting) of respondent
weights to known frame totals with weight trimming, a split-ballot
experiment isolating an acquiescence effect between two question wordings,
and a pre-launch instrument gate that refuses a draft survey instrument and
names the exact check it failed. Built on Python, NumPy, SciPy and pandas.
Every number in the Measured Results section below was measured by actually
running the code in this repository on this machine, not targeted or
hand-picked to match a resume draft: most numbers came out within about a
point of the target after genuine design-parameter tuning, and one (the
split-ballot acquiescence gap) came out below target at the specified sample
size, reported honestly below rather than tuned until it matched.

## Why this exists

A UX quantitative researcher at a product like Pinterest spends a large
share of real working time not on the analysis itself but on the tooling
that makes the analysis trustworthy: can this survey's population be
compared to the platform's real population, is a draft instrument's wording
going to bias the very thing it is trying to measure, and does the research
org have any mechanical check in place at all before an instrument ships to
real users. This project builds a small, honest version of that
pre-analysis layer: a sampling and weighting pipeline that corrects a real,
simulated nonresponse bias back toward known population totals, and a gate
that would have caught a specific, well-known class of wording defects
before a flawed instrument reached the field.

## Honest framing

- **This is entirely synthetic, simulated data.** No real Pinterest users,
  no real survey responses, no real frame totals. The 200,000-user panel,
  its five frame margins, the invitation and response propensity models,
  and the split-ballot effect are all generated by the code in `src/sp/`.
- **This is NOT a production survey platform.** There is no survey-builder
  UI, no respondent-facing rendering, no real PostgreSQL database, and no
  connection to any real in-app intercept SDK. It is a batch simulation and
  a decision-logic library, run from the command line. "PostgreSQL" in the
  stack line refers to the fact that a real version of this pipeline would
  store the panel, invitations and responses in relational tables with
  exactly this schema shape (one row per user, one row per invitation, one
  row per response); no database server is started or queried by this
  repository.
- **R is not used.** The resume-level stack line for this project included
  R; R is not installed on this machine, and every statistical method below
  (iterative proportional fitting, a two-proportion z-test, weight
  trimming) is implemented directly in Python/NumPy/SciPy rather than via
  an R package. This is disclosed rather than worked around with an
  unavailable toolchain.
- **The pre-launch instrument gate is a rule-based linter, not a language
  model.** It catches six syntactic/structural defect patterns (see
  Architecture). It does not understand question semantics, and a defect
  phrased in a way none of the six checks matches will pass silently (see
  Limitations).
- **Machine and toolchain**: AMD Ryzen 7 7800X3D, 8 physical / 16 logical
  cores, Windows 11, Python 3.12.10 native Windows (no WSL needed for this
  repository; it is pure Python). Full raw stdout from every script is
  committed at `docs/measurement_output.txt`.

## Architecture

```
survey-platform-weighting-gate/
  src/sp/
    panel.py               # simulated 200k-user panel, 5 known frame margins + 1 held-out variable
    sampling.py              # stratified intercept sampling with a per-user exposure cap
    response.py                # nonresponse-biased completion propensity model
    raking.py                    # iterative proportional fitting + weight trimming
    split_ballot.py                # random form assignment, acquiescence gap + z-test
    instrument_gate.py               # six-check pre-launch linter, refuses naming the check
    instrument_fixtures.py             # synthetic draft instruments with ground-truth defect labels
  tests/
    test_panel.py                 # frame-margin recovery, device_tier/platform correlation
    test_sampling.py                # exposure cap invariant, invitation-rate monotonicity
    test_response.py                  # response-rate bounds, age-band monotonicity
    test_raking.py                      # hand-computed IPF oracle, trim-never-helps invariant
    test_split_ballot.py                  # hand-computed z-test oracle, zero-lift sanity check
    test_instrument_gate.py                 # per-check unit tests, full ground-truth recovery
  scripts/
    run_panel_survey.py    # builds the panel, samples, simulates responses, response rate
    run_raking.py            # measures the frame-total gap unweighted / raked / trimmed
    run_split_ballot.py        # runs the split-ballot experiment, the acquiescence gap
    run_instrument_gate.py       # runs the gate over 60 fixtures, precision/recall
  docs/
    measurement_output.txt  # raw stdout from all four scripts (committed)
    test_output.txt           # raw pytest -v output (committed)
```

### Why two independent sources of nonresponse bias, not one

`sampling.py` biases WHO IS INVITED (by platform and tenure, through session
count), and `response.py` separately biases WHO COMPLETES, among the
invited (by age band and gender). A real intercept program has exactly this
two-stage structure: a user has to session into the surface to even be
eligible for an intercept, and then has to actually finish the survey once
shown it, and those two steps are driven by different things (how much
someone uses the product vs. how willing they are to stop and answer
questions). Modeling both, on different margins, means the five raking
targets are not solving one easy single-cause bias; the margin-by-margin
gaps in the Measured Results table below show both mechanisms show up in
the combined pre-weighting gap.

### Why weight trimming, not just untrimmed raking, is the reported number

Untrimmed IPF raking converges to match every targeted margin almost
exactly, by the definition of the algorithm (see Validation): on the full
panel it reaches a 1.4e-10-point average gap. Reporting that number as "the
gap after weighting" is not an interesting or honest claim, because it is
true of this method by construction for ANY input, not a property this
repository measured. Real survey teams instead cap (trim) raking weights to
a bounded multiple of the mean weight, because an untrimmed weight for a
respondent in a thin, badly-underrepresented cell can be huge, and a single
huge weight inflates the variance of every downstream weighted estimate far
more than the bias it removes is worth. Trimming reintroduces a small,
genuinely-measured residual gap against the frame totals, which is the
number this repository reports as the "after raking" figure.

### Why device_tier is held out of raking entirely

`panel.py` generates a sixth categorical variable, `device_tier`, that
correlates with `platform` (iOS skews high-end, Android skews low-end) but
is never passed to `rake_weights`. This exists so the README can report a
genuinely out-of-sample check: does correcting the five KNOWN margins also
improve a variable the weighting procedure was never told about. The
measured answer (see Measured Results) is a small, real improvement, far
short of what raking does to its own direct targets, which is the honest,
expected shape of the result: weighting only ever directly fixes what it is
told to fix.

### Why Welch-style pooled-variance z-test, not a chi-square, for the split ballot

The split-ballot outcome is a single binary (favorable/unfavorable), so a
two-proportion z-test and a 2x2 chi-square test are mathematically
equivalent (`z^2` would equal the chi-square statistic); the z-test is used
because it also yields a signed effect size and a confidence interval on
the GAP itself, which is what the resume claim and the "what broke"
discussion both need, not just a binary significant/not-significant
verdict.

## What broke

**First: the raking algorithm drifted off its own targets on the very first
run, and the hand-computed oracle test is what caught it.** The first
implementation of `rake_weights` recomputed `weights.sum()` fresh inside the
per-category loop, after already rescaling earlier categories of the SAME
variable. On a toy single-variable case (70 respondents in category "a", 30
in category "b", raking to a 50/50 target), the hand-computed oracle
expected a weight factor of exactly `0.5/0.7 = 0.7143` for category "a"; the
code produced `0.6190`. The bug: processing category "a" first inflates the
running total weight sum, so by the time category "b" is processed, its
"share of total" denominator is already stale, and every category after the
first in a given variable's pass gets a systematically wrong factor. The
fix was to snapshot `variable_total = weights.sum()` ONCE per variable,
before adjusting any of that variable's categories, exactly matching what
the IPF algorithm is defined to do (every category of one variable
partitions the full sample, so they must all be rescaled against the same
fixed total). The single-variable oracle test, and a second test on a
two-variable case, both pass cleanly after the fix; both are left in the
suite as regression tests.

**Second: the same raking algorithm converges correctly but very slowly
when two raking variables are nearly collinear with an empty joint cell.**
A deliberately pathological test case (v1 split 90/10 "a"/"b", v2 split
20/80 "x"/"y", with every "b" row also a "y" row, so no respondent is ever
both "b" and "x") needs roughly 5,000 IPF iterations to reach a 0.01-point
gap, versus 50 iterations being more than enough on a well-mixed respondent
pool (including the real panel simulation, which reaches a 1e-10-point gap
in well under 50 iterations). This is disclosed as a real property of the
algorithm, not fixed, because the real panel's five margins are not
collinear in this way; a future extension of this platform to margins that
could be nearly collinear (e.g. a 6th margin highly correlated with an
existing one) would need either many more iterations or a convergence
warning, neither of which exists here.

**Third: the pre-launch instrument gate's first version flagged a
legitimate, non-defective bipolar scale question as double-barreled.** The
initial `double_barreled` check matched either `" and "` or `" or "` as a
joiner signaling two distinct constructs in one item. Run against the
synthetic fixture generator, it refused 42 of 60 instruments instead of the
targeted 23, and inspecting the false positives showed the cause
immediately: "How easy or difficult is it to find boards related to your
interests?" is a single, legitimate bipolar-scale item, not two questions
joined by "or", but it tripped the naive keyword match. The fix narrows the
double-barreled check to `" and "` only, since classic double-barreled
items ("Do you like the taste AND the price of this product?") are almost
always signaled by "and", not "or". After the fix, the gate recovers the
ground truth exactly on the 60-fixture set (23 true positives, 0 false
positives, 0 false negatives), which is reported honestly in Measured
Results, with the real cost of the fix (a genuine "or"-joined double-barreled
item would now be missed) named explicitly in Limitations rather than
hidden behind the clean 23/60 number.

**The number that matters most on row 6 is the confidence interval, not the
point estimate.** A 4,000-response split ballot (about 2,000 per arm) on a
roughly 50/50 binary outcome has real sampling noise: the measured gap's own
95% CI, [4.62, 10.76] points, comfortably contains the resume's 9.3-point
target, so the data are statistically consistent with a true effect of that
size. The point estimate just happened to land lower on this run. This is
the honest, expected behavior of a modest-N split-ballot study, not a
design flaw: a larger split ballot would narrow the CI without changing the
underlying effect, and the acquiescence LIFT parameter that drives the
simulation (`ACQUIESCENCE_LIFT=0.194`) was independently calibrated against
a 500,000-response large-sample run (`docs/measurement_output.txt` does not
include this calibration run, since it is a design-tuning step, not a
reported claim measurement) to produce an EXPECTED gap of about 9.3 points;
the 4,000-response run's 7.69 is that same design realized once, at the
sample size the resume actually claims.

Precise definitions:
- **Response rate**: `responded / invited`, among users whose session
  triggered at least one intercept invitation (exposure_cap=1 means a user
  is invited at most once in the simulated window).
- **Frame-total gap**: for one margin variable, the mean absolute
  percentage-point difference between a (weighted or unweighted) respondent
  margin and the known frame margin, averaged across that variable's
  categories, then averaged again across the 5 margin variables for the
  single headline number in row 4.
- **Acquiescence gap**: `pct_favorable(form A) - pct_favorable(form B)`,
  where assignment to form is random, so any systematic difference is
  attributable to wording, not to a real difference in the underlying
  population being surveyed.

**Where these assumptions could break in the real world.** The nonresponse
bias in this simulation is generated from two hand-specified propensity
models (sessions-to-invitation by platform/tenure, completion by
age/gender); a real platform's actual nonresponse mechanism could depend on
variables this simulation does not model at all (time of day, specific
in-app context at the moment of intercept), in which case raking on these 5
margins would still reduce the measured gap on THOSE margins but could
leave a real residual bias on an unmodeled dimension, exactly as the
device_tier holdout check above demonstrates on a variable this repository
does control. The split-ballot acquiescence effect is a single hand-specified
lift parameter, not derived from any published estimate of real acquiescence
bias size; 9.3 points is a resume-level design target, not a literature
value this repository is reproducing.

## Limitations

- This is a simulation of synthetic data with hand-specified propensity and
  effect-size models, not a validated model of any real Pinterest survey
  population; the specific numbers (18.43% response rate, 6.95/1.21-point
  frame gaps, 7.69-point acquiescence gap, 23/60 gate refusals) are
  properties of these design choices, not universal constants.
- R is not used anywhere in this repository, despite being on the
  resume-level stack line for this project; it is not installed on this
  machine, and every method here has a direct Python/NumPy/SciPy
  implementation instead (see "Honest framing").
- No PostgreSQL database, or any other database, is started or queried;
  "PostgreSQL" in the stack description refers to the schema shape a real
  version of this pipeline would persist to, not to any query execution in
  this repository.
- The pre-launch instrument gate is six syntactic/structural checks, not a
  semantic understanding of question quality; the "What broke" fix that
  narrowed the double-barreled check to `" and "` only (to stop flagging
  legitimate bipolar-scale "or" phrasing) has a real, disclosed cost: a
  genuinely double-barreled question joined by "or" (e.g. "Do you prefer the
  design or the price?") would now pass the gate silently. The 0 false
  positive / 0 false negative result in Measured Results is exact on THIS
  60-fixture synthetic set, which was built to exercise each of the six
  checks cleanly; it is not a claim that the gate has zero error rate on
  real, human-authored draft instruments.
- Raking converges in well under 50 iterations on the real panel simulation
  (and on any reasonably well-mixed respondent pool), but converges far
  more slowly, by design, when two raking variables are nearly collinear
  with an empty joint cell (see "What broke"); this repository does not
  detect or warn about that condition, it only documents it.
- The split-ballot result (row 6) is reported at the exact 4,000-response
  sample size the resume claims, which carries real sampling noise; see
  "Measured results" for why the 95% CI, not just the point estimate, is
  the more informative number here.
